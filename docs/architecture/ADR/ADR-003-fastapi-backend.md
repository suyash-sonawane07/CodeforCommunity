# ADR-003 — FastAPI backend

- **Status:** Accepted · **Date:** 2026-09-27 · **Owner:** Member B

## Context
Both research reports (PRD §12) direct Python + FastAPI; the team is AI/Data Science —
Python keeps the `ai/` layer and analytics tooling (Pandas, scikit-learn) in one language.
Three members must integrate independently → the API contract must be self-describing.

## Decision
FastAPI + Pydantic v2 + SQLAlchemy 2 (sync sessions) + Alembic. OpenAPI generated by
FastAPI is the binding frontend/backend contract, exported to
`docs/api/openapi/openapi.json` via `backend/scripts/export_openapi.py`
(`make openapi-export`). Every PRD endpoint (§10.1) exists as a router with real
request/response schemas and returns `501 NOT_IMPLEMENTED` until implemented.

## Reason
Auto OpenAPI docs let Member A build against the contract before endpoints exist
(PRD R-07 mitigation); Pydantic gives validation-ready schemas; async support if needed.

## Alternatives
Node/Express (rejected in PRD — worse fit for the AI stage reuse); Django (rejected —
heavier, split-brain ORM/serialiser conventions for a small team); Flask (rejected —
no automatic OpenAPI/validation).

## Consequences
- Python 3.9+ required (no newer-syntax-only code in `backend/` or `ai/`).
- Contract drift is visible: CI exports OpenAPI and fails if the committed spec is stale.
- 501 placeholders keep schemas discoverable without faking success.
